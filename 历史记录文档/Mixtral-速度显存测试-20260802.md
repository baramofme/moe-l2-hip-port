# Mixtral 8x7B 速度与显存测试（2026-08-02）

> 测试目的：主线验证——大专家模型（Mixtral 每专家 ~1.7GB）在方案 F 形态下的速度/显存，以及 LRU expert cache 在大专家上的价值
> 测试环境：AutoDL RTX 4090（24.5GB VRAM），llama.cpp-clean/build-a3（方案 F 成品二进制，含 expert-cache LRU 实现）
> 模型：Mixtral-8x7B-Instruct-v0.1.Q4_K_M.gguf（28,448,468,384 字节，28.4GB，GGUF v3，arch=llama，32 层 × 8 专家，top-2 激活）
> 前置修复：fattn.cu:382 的 [FADBG] 调试打印（moe-l2 debug，每 10 次打一条）已禁用（`if (0 && ...)`），重编 libggml-cuda.so —— 否则加载阶段起刷屏 2200 万行/1GB+，拖死推理并污染测速
> 测试方法：每档独立跑 llama-cli --single-turn，-p 'Hello, what is 2+2?' -n 30，运行中循环采样 nvidia-smi 显存峰值

## 二、关键发现

### 1. LRU cache 完全无效，根因：cache 从未被触发
- `[A3] expert_cache initialized` 打印计数 = **0**（grep -ac '\[A3\]' 输出 0，只有 A3TIME mul_mat 计时打印）
- A3 cache 实现挂在 GPU cuBLAS mul_mat 路径（ggml-cuda.cu:1455 expert_cache_get），但方案 F 形态下**专家计算全在 CPU**（mmap 默认，专家 tensor 留 CPU RAM）
- 四档 VRAM 恒定 2193 MiB 证实：cache 没分配任何 slot，专家没走 GPU 路径
- **不是"大专家 cache 无价值"，是 cache 对"专家 CPU"形态完全不生效**

### 2. -ngl 8→99 只加显存不加速度
- 显存 1279 → 2193 MiB（attention/非专家层逐层上 GPU）
- Gen 速度 2.5 → 2.7 t/s（几乎不变）——瓶颈在 CPU 专家计算
- 与方向 1 发现闭环：llama.cpp 默认调度器把专家 mul_mat 留在 CPU，-ngl 不碰专家

### 3. Mixtral 8x7B 在 4090 上的部署现实
- 全 GPU 放不下：专家 ~23GB + 非专家 ~3GB > 24.5GB VRAM
- 方案 F（专家 CPU）只有 2.7 t/s：8x7B 的 90% 参数是专家，CPU 算不动
- 比 DS（13-14 t/s）慢 5 倍、比 Qwen（10-11 t/s）慢 4 倍

## 三、结论与下一步

1. **主线验证结论修正**：LRU cache 的价值验证必须先解决"专家走 GPU"——方案 F（专家 CPU）形态下 cache 是死代码
2. **方向 1（专家 GPU 化 DMA 直读）是唯一能让 Mixtral 类大专家模型受益 cache 的路线**，但方向 1 在 DS 上实测 9.06 t/s（-28% 慢于 CPU 12.46），机制通、性能不划算；且 Mixtral 28GB 全 GPU 放不下，需 expert 粒度 offload（只上热专家）——这正是 A3 cache 设计目标，但需要 cache 在"专家 CPU→GPU 动态搬运"路径上生效（当前实现挂在 cuBLAS mul_mat 内，只服务已上 GPU 的专家）
3. **Mixtral 作为主线测试对象的价值**：证实了"大专家模型必须专家 GPU 化才有提速空间"，但也暴露 cache 实现与方案 F 形态不兼容（cache 服务 GPU 专家，方案 F 专家在 CPU）

## 五、--no-mmap 收官测试（2026-08-02，根因确诊）

> 上文测试均为 mmap 默认形态（专家留 CPU RAM）。收官测试加 `--no-mmap` 跑同一 Mixtral 模型，目标：验证"专家全量上 GPU"时 cache 是否有价值。

### 5.1 测试配置与数据

- 命令：`llama-cli --single-turn -p 'Hello, what is 2+2?' -n 40 -ngl 99 --no-mmap --no-warmup -c 2048`
- 环境：`GGML_OP_OFFLOAD_MIN_BATCH=1` + `GGML_CUDA_EXPERT_CACHE=<档位>`
- 对比组：cache 0.25 / 0.5（命中率实测 27.3% / 48.7%），以及无 cache 对照

| 配置 | Gen t/s | mmid avg | 命中率 |
|------|---------|----------|--------|
| 无 cache（--no-mmap） | 3.7 | 7-15 µs（快路径） | — |
| cache 0.25 | ~3.4 | 3060 µs | 27.3% |
| cache 0.5 | ~3.4 | 3100 µs | 48.7% |

### 5.2 根因结论（确诊）

1. **--no-mmap 下专家已全驻 GPU**：copy kind 实测全为 D2D、dev_ratio=100% —— 调度器输入拷贝把专家权重全量搬上 GPU。3.7 t/s 就是"专家全驻 GPU 直接算"，**mmap 形态作废**，根本不存在 PCIe DMA 直读 CPU 专家这回事。
2. **命中不省时 = mmid 3.1ms 慢速管线固定开销**：`GGML_CUDA_EXPERT_CACHE` 一开 → `a3_on=true` → `goto skip_early_returns` 强制跳过 early-return 快路径（无 cache 时走 `ggml_cuda_mul_mat_vec_q` 直接 return，mmid 7-15 µs）；有 cache 时被迫走通用 MUL_MAT_ID 慢速管线：ids D2H + 同步 → CPU 排序 → ids H2D + 同步 → get_rows → per-expert 循环。
3. **3.1ms 与 cache 无关**：分段计时拆开 per-expert 循环实测——get 0.2µs / alloc 0.1µs / copy_sync 65.6µs (D2D) / vec 54.6µs，循环内全部开销 ≈ 250µs，但 mmid avg = 3271µs，**3.0ms 在循环之外**（ids 同步 + get_rows 固定开销）。命中率翻倍（27.3% → 48.7%）mmid 纹丝不动（3060 → 3100µs），命中收益（~65µs）在 3ms 固定开销面前不可见。
4. **cache 对 --no-mmap 无价值（纯多余层）**：专家本就在 GPU，cache 的"CPU 专家搬 GPU"机制无对象，只会强制走慢速管线把 3.7 t/s 拖到 3.4 t/s。已排除：cudaPointerGetAttributes 同步校验、temp_gpu alloc、get 线性扫描、miss 双拷贝、第 2 个 cudaStreamSynchronize。
5. **实现备注**：A3 开关经 env 通道生效（弱符号跨 DSO 失败 → setenv/getenv 方案）；后续若修 a3_on 逻辑（只在专家真在 CPU 的 mmap 形态启用 A3 管线），需用户定夺。

### 5.3 结论修正（相对第三节）

- 上文第三节结论"cache 对方案 F（专家 CPU）不生效"成立；收官测试补充：**cache 对 --no-mmap（专家全驻 GPU）同样无价值**，且有害（强制慢速管线 -0.3 t/s）。
- 三档 DMA 全矩阵（0.5/1.0 更大容量）不必再跑：此形态 cache 无用已盖棺。
- cache 的适用形态收窄为：**mmap 默认 + 专家真在 CPU RAM + 走 GPU 计算路径**（方案 F 的 A3 per-expert dispatch 形态），即只有"专家 CPU 驻留"才有 cache 意义。

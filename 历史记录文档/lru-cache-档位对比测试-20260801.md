# LRU Expert Cache 档位对比测试（2026-08-01 原始 / 2026-08-02 干净复测）

> 测试目的：验证 LRU expert cache 在不同 cache 档位下的速度/显存表现，找最优平衡点
> 测试环境：AutoDL RTX 4090（24.5GB VRAM），llama.cpp-clean/build-a3（方案 F 成品二进制，含 expert-cache LRU 实现）
> 启动参数：`-ngl 99 -c 2048`，`GGML_CUDA_EXPERT_CACHE=<档位>`，无 A2（不设 GGML_CUDA_EXPERT_CACHE 以外的开关）
> 测试方法：每档位独立跑 llama-cli --single-turn，`-p 'Hello, what is 2+2?' -n 30`，后台循环采样 nvidia-smi 显存峰值

> ⚠️ **2026-08-02 复测修正**：原 08-01 数据被 FADBG 调试打印污染（fattn.cu:382 每 10 次打一条，刷屏拖慢推理并污染测速）。复测在 FADBG 禁用 + 修 a3_on 后的干净二进制上跑，全日志确认无 FADBG。

> ⚠️ **2026-08-02 复测形态说明（重要）**：08-01 旧数据与 08-02 第一轮复测均为**专家 CPU 后端算形态**（mmap 默认、无 GGML_OP_OFFLOAD_MIN_BATCH，日志 mmid avg=0，cache 未进 GPU 路径）。08-02 第二轮补测**专家走 GPU 计算路径形态**（GGML_OP_OFFLOAD_MIN_BATCH=1，mmid 出现）——两形态结论一致：**cache 均无收益**。

## 五、根因分析

1. **专家 CPU 算形态下 cache 根本不参与**：方案 F（mmap 默认）专家 MUL_MAT_ID 在 CPU 后端算（日志 mmid avg=0），GGML_CUDA_EXPERT_CACHE 只影响 GPU 侧 mul_mat_id 路径——专家没进 GPU 路径，cache 是死代码。**速度差异 = 运行噪声，非 cache 效果。**

2. **专家走 GPU 路径形态下 cache 同样不参与**（08-02 第二轮复测）：GGML_OP_OFFLOAD_MIN_BATCH=1 时专家 op 派 GPU、sched 输入拷贝把专家从 CPU 全量搬到 GPU 后，src0->data 指针变为 Device 类型 → 修 a3_on 后的 `ggml_cuda_experts_on_host()` 返回 false → A3/cache 管线被跳过（走 GPU 快路径 mmid ~12µs）。**cache 触发条件（专家真在 CPU 且走 A3 慢速管线）在当前任何形态都不满足。**

3. **cache 的真实价值场景**（理论上）：专家真在 CPU + 不走 sched 全量拷贝、而是 kernel 直读 CPU 指针（旧版 llama.cpp DMA 直读行为）时，A3 cache 才有机会命中省搬运——但该形态当前代码已不可达（sched 拷贝先行）。大专家模型（Mixtral ~252MB）才有显著收益空间，但 24GB 卡放不下全量专家。

4. **修 a3_on 后的行为变化**：--no-mmap（专家全驻 GPU）+ cache 不再强制走慢速管线（mmid 3.1ms→17µs，Gen 3.4→3.6 t/s）；mmap 形态 A3 管线不变。详见 `Mixtral-速度显存测试-20260802.md` §5 和产品化方案文档。

## 九、方向 1：专家 GPU 化（DMA 直读架构）完整验证（2026-08-01 追加）

> 目标：实现"专家 mmap 在 CPU RAM（不占 VRAM）+ GPU 经 PCIe DMA 直读计算 + 热专家 cache 留 GPU"的原始架构
> 基线：llama.cpp-clean/build-a3（方案 F 二进制），DS-V2-Lite Q2_K，RTX 4090

### 8.1 关键发现：方案 F 的专家其实在 CPU 算

- 加 SCHED-CHECK 日志（ggml_cuda_mul_mat_id 入口检测 src0 指针类型）后发现：
  **方案 F（!buft fix 强制 CPU buffer）下 MUL_MAT_ID 从没进入 GPU 路径**（日志只有 "mul_mat avg"=attention 层，没有 "mmid avg"=专家层）
- 结论：方案 F 的 12 t/s 是 **CPU 算专家**，GPU 只算 attention 等非专家层
- 这解释了之前 LRU cache / pinned 注册收益小的原因：专家根本不在 GPU 路径上

### 8.2 机制打通步骤

| 步骤 | 改动 | 效果 |
|------|------|------|
| 1. cudaHostRegister 接线 | llama-model-loader.cpp load_data_for() 对 MUL_MAT_ID 专家调 register_host_buffer（GGML_CUDA_REGISTER_HOST=1 触发） | pinned 内存，H2D 拷贝更快（DS 12.02→12.54-13.47，+4-12% ✅；Qwen 10.7→9.7-10.4 略降 ❌） |
| 2. !buft fix 改用 CUDA host buffer | 专家 buft 从 CPU buffer 改为 `ggml_backend_dev_host_buffer_type(gpu_dev)` | 数据在 CPU pinned（不占 VRAM）+ backend 是 CUDA（GPU 算） |
| 3. GGML_OP_OFFLOAD_MIN_BATCH=1 | sched 默认 32，DS batch<32 时专家不 offload 到 GPU；设为 1 强制 | **专家终于走 GPU（mmid avg 12.4µs 出现）** |

### 8.3 实测数据汇总

| 配置 | 专家计算位置 | Gen t/s | VRAM | 崩溃 | 输出 |
|------|------------|---------|------|------|------|
| 方案 F（CPU buffer） | CPU | 12.46 | 1133 MiB | 无 | ✅ |
| GGML_CUDA_REGISTER_HOST=1（pinned 注册） | CPU | 12.54-13.47 | 1209 MiB | 无 | ✅ |
| CUDA host buffer + MIN_BATCH=1 | **GPU** | **9.06** | 1209 MiB | 无 | ✅ |
| GPU offload + LRU cache=0.25 | GPU + A3 cache(16 slots) | 8.96-9.20 | 1243 MiB | 无 | ✅ |

### 8.4 关键结论

1. **专家 GPU 化机制全部打通**（host buffer → sched 派 GPU → GPU mul_mat_id 计算），你的架构技术路径验证成立
2. **但速度反而比 CPU 版慢 28%**（9.0 vs 12.46 t/s）：
   - sched 把激活专家 H2D 拷贝到 GPU（input_cpy）→ 每次生成都有拷贝开销
   - DS 专家太小（1.55MB），拷贝 60µs × 28 层 × 每 token 累加 > CPU 直接算
3. **LRU cache 叠加无效**（8.96-9.20，与无 cache 持平）：走 A3 cache 路径后 mmid avg 从 12.4µs 暴涨到 **194-254µs**——cache 的查找/替换开销远大于直接搬运收益
4. **最终判断**：DS 上专家 GPU 化机制成立但性能不划算——与 scheme-h 分析一致（DS 专家层只占 3% 时间，专家 GPU 化收益被搬运开销淹没）；Qwen 专家层占 93% 但专家更小（1MB），同样被搬运成本吃掉
5. **为什么 Qwen 注册也无收益**：Qwen 专家 256/层、top-8、40 层，且 IQ2_M 走 dequant 路径，注册/直读收益被 dequant 计算开销淹没

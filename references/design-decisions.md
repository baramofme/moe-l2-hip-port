# moe-l2 设计决策记录（Design Decisions）

> 为什么最终是 host-buffer 方案？本文记录从 2026-07 至今的完整方案演进史。
> 每条记录格式：目标 → 实测结果 → 为什么放弃/保留。
> 只写方案层面的取舍，不涉及实现细节。

---

## 0. 背景与核心洞察

**目标**：让 8GB 及以下的消费级显卡运行 16GB+ 的 MoE 模型（Qwen3-30B-A3B、Qwen3.6-35B-A3B、DeepSeek-V2 等），并保持可用的推理速度。

**核心洞察**：MoE 模型每步推理只激活少量专家（top-2 ~ top-8，数百个专家中的几个）。把全部专家权重常驻显存是浪费——大多数专家在大多数时间不被使用。如果专家权重驻留在 CPU 内存（零显存），GPU 每步只取被激活的专家计算，理论上可以用极小显存跑超大模型。

围绕"如何把专家从 CPU 内存高效送到 GPU 计算"这个问题，我们走了三个阶段、十余条技术路线。

---

## 1. 阶段一：架构选型（2026-07-21）

| 方案 | 思路 | 结果 |
|------|------|------|
| **A：社区方案复现** | 直接使用 MoE-Infinity / Mixtral-offloading | ❌ 淘汰：对硬件依赖高、只支持特定架构、不支持 GGUF 格式，试了几天走不通 |
| **B：自研三级调度** | CPU mmap 共享内存 + 领域预测器 + 专家按需搬运 | ✅ **选中**：路线可控，每步可验证 |
| **C：双轨并行** | A/B 深度并行，谁先通用谁 | ❌ 淘汰：4 核 CPU 设备无法同时支撑两套开发 |

---

## 2. 阶段二：三级调度的实现路径探索（2026-07-23）

选中方案 B 后，对"如何控制专家内存"探索了三条路径：

### 路径 1：不加 --mlock 直接跑（0 行代码）
- **思路**：依赖操作系统 mmap 按需分页，推理时只访问被激活的专家页
- **实测**：加载 13 分钟+，进程 RSS 峰值 23.3GB，RAM 占用 31GB + 13GB swap，无有效输出
- **为什么放弃**：llama.cpp 的 warmup 阶段会遍历全部专家（n_expert_used = 全量），一次性调入所有页；且推理图构建/allocator 阶段也会触碰全部专家 tensor 头。操作系统页粒度（4KB）远大于"控制单专家"的诉求，不拆结构就控不住内存
- **结论**：必须改 C++ 代码，纯配置无解

### 路径 2：加载时拆 expert tensor（3-4 天工作量）
- **思路**：把 3D expert tensor 拆成 N 个独立 2D tensor，每个专家独立 mmap
- **为什么搁置**：改动横跨模型加载/图构建/推理调度三个核心路径，且破坏 GGUF 社区命名约定。路径 3 用更小的改动可以达到同样效果

### 路径 3：推理循环中动态管理内存（最终方向）
在路径 3 下评估了 8 种具体做法：

| 做法 | 思路 | 结果 |
|------|------|------|
| A：MUL_MAT_ID 内释放 | 专家算完立刻 madvise 释放页 | ✅ 实施（~20 行 C），验证可跑 |
| B：willneed/dontneed | 在 graph_compute 前后操作 | 并入做法 G |
| C：backend_sched split 边界回调 | split 边界插释放 | ❌ 不推荐：split 不等于层边界，架构改动大 |
| D：ggml_cplan 线程回调 | 每 op 执行完插入回调 | ❌ 不通：现代 llama.cpp 走 backend_sched，绕过了该路径 |
| E：GGUF 文件重排专家 | Python 重写 GGUF 让专家连续 | ❌ 不再需要：实测发现 Q2_K 量化后专家**本来就是连续排列的**，重排无意义 |
| F：mincore 检查 + madvise | 用 mincore 判断页是否在内存 | 并入做法 A（做法 A 更直接） |
| G：逐层构建和执行子图 | decode 改为逐层 build+compute+release | ⭐ 曾重点推进，后被 host-buffer 取代（见阶段三） |
| H：MAP_FIXED 虚拟地址分片 | 每专家独立 mmap 映射 | ❌ 不推荐：1728 个 VMA 碎片 + 频繁系统调用 |

**关键发现（改变路线走向）**：Q2_K 量化后专家数据在内存中按专家连续排列（不是行交错）。这个发现让"按专家控制页"成为可能，是后续所有方案的前提。

## 3. 阶段三：从"省内存"到"专家 GPU 化"（2026-07 底 ~ 2026-08-02）

前两个阶段解决了"内存控制"，但暴露了新问题：**内存省下来了，速度不行**。于是开始围绕"专家到底在哪算"做方案迭代。

### 方案 F：--cpu-moe（专家在 CPU 计算）
- **思路**：利用 llama.cpp 原生 `--n-cpu-moe` 参数，把 MoE 专家留在 CPU 计算，GPU 只跑非专家层。零 C++ 改造
- **实测（RTX 4090）**：DeepSeek-V2-Lite ~12.5 t/s；Qwen3.6-35B-A3B ~9 t/s；Mixtral 2.7 t/s（8x7B 的 90% 参数是专家，CPU 算不动）
- **为什么放弃**：专家占 MoE 模型 ~90% 计算量，CPU 算专家的速度上限就是个位数到十几 t/s。**能跑，但体验不可用**。Mixtral 测试还证实：大专家模型（每专家 ~1.7GB）必须专家 GPU 化才有提速空间

### 方案 G：逐层调度（deepseek2.cpp 改造）
- **思路**：改 decode 流程为逐层 build+compute+release，每层只保留该层活跃专家的页
- **为什么放弃**：被 host-buffer 方案取代——host-buffer 用更小的改动（专家 CPU pinned + 调度器按需拷贝）达成了同样的目标，无需动 decode 核心流程

### A2：专家 GPU 化按需打包
- **思路**：把被激活的专家按需打包传到 GPU 计算，绕开"全量上 GPU"的显存需求
- **实测（Qwen3.6-35B）**：10.76 t/s、VRAM 2.2GB——比方案 F 快但远未达目标（40-100 t/s）
- **卡点**：DS 回归失败（改动后 DS 输出变垃圾）、Qwen 槽位未全对（输出 '20,20' 未到终点）。每次搬运开销抵消了 GPU 算力优势
- **结论**：方向对，但"按需打包"的工程复杂度高，收益被搬运开销吃掉

### ✅ host-buffer：最终方案（专家 CPU 驻留 + GPU 直算）
- **思路**：专家权重驻留 CPU 内存（pinned，零显存），GPU 通过调度器每步只把**被激活的专家**拷贝到显存计算，热专家用 LRU 缓存留在 GPU 免 PCIe 往返
- **实测（RTX 4090，2026-08-02）**：
  - DeepSeek-V2-Lite：12.5 → **37.5 t/s**（+200%），VRAM 1.6 GB
  - Qwen3.6-35B-A3B：10 → **46.8 t/s**（+370%），VRAM 2.1 GB
- **为什么它赢了**：
  1. 专家在 GPU 算（不是 CPU）——绕开方案 F 的速度天花板
  2. 按"激活专家"粒度搬运而非全量——绕开显存瓶颈
  3. 改动集中在调度器拷贝层（挂 sched 拷贝钩子），不动 decode 核心流程——绕开方案 G 的工程复杂度
- **配套优化**：
  - **sched-cache**（2026-08-02）：在调度器拷贝层加专家缓存。DS Prompt 99 → 308 t/s（+211%，cache=0.25），VRAM 不变；Qwen 专家太小无收益，按模型开关
  - **多架构二进制**（bins-v0.2.1）：一个二进制支持 GTX 1080（sm_61）→ RTX 50 系（sm_120a），三卡实测 2080 Ti 6.89 / 3080 Ti 12.25 / 5090 16.63 t/s

## 4. 技术边界（诚实声明）

### 框架行为观察：22GB 中间缓冲区的真相（llama.cpp 生态理解）

> 这是对 llama.cpp 框架行为的分析结论，非 moe-l2 实现细节——公开供生态参考。

**现象**：DS-V2-Lite（6GB Q2_K）在无 GPU 环境下推理，RSS 峰值高达 23.3GB，远超模型本身大小。

**常见误解**：以为 22GB 是 warmup 阶段全量加载专家（n_expert_used=64）造成的。

**真相**（2026-08-28 修正）：
1. `cparams.warmup` 早已 deprecated，实际推理永远走 `n_expert_used=6`（正常激活数），与 warmup 无关
2. 22GB 的构成：prefill 阶段（n_tokens 大，512~2048）的 attention 大矩阵（kq/kq_mask，~14GB）+ MoE 中间结果（~1.6GB）+ KV cache（~1.5GB）+ 权重文件页调入（~6GB）+ ggml-alloc chunk padding
3. **根因是 ggml-alloc 的一次性分配策略**：首次 prefill 按大 n_tokens 一次性 malloc 全部中间 buffer（~22GB 匿名页）；后续 decode（n_tokens=1）时 `needs_realloc` 检查发现新 tensor ≤ 已分配大小 → 判定不需要 realloc → **prefill 的峰值 buffer 永久残留，不缩容**
4. decode 1 token 实际只需要每层 ~5-10MB 中间 buffer——22GB 是 prefill 峰值残留，不是 decode 的真实需求

**对生态的意义**：任何 llama.cpp 用户跑长 prompt prefill 后，RSS 都会永久保留 prefill 峰值，即使后续全是单 token decode。这是 ggml-alloc 复用策略的固有行为（"allocate once, reuse forever"），不是 bug，但值得生态知晓——尤其在内存受限设备（8GB 内存的迷你主机/树莓派）上，prefill 峰值可能直接决定能否运行。

### 235B 终极验证（Qwen3-235B-A22B，2026-08-02）
- **已验证**：8GB 卡可运行 81.7GB 的 235B MoE（Q2_K），证明"小显存跑大模型"上限成立
- **速度**：~1 t/s——这是 22B 激活参数在单卡 4090 上的算力物理极限（SM 82% 满载，瓶颈是 GPU 计算本身而非搬运/缓存/调度）
- **定位**：演示/技术验证性质，不作为性能卖点。三条提速路线（预测预加载 / UVA 直读 / cache 扩容）全部验证封死：
  - 预测预加载：相邻 token 专家重叠仅 42% 天花板，预载负收益
  - UVA 直读（cudaHostRegister）：直读 5.8 GB/s vs cudaMemcpy 25.1 GB/s（慢 4 倍），cuBLAS 吃 UVA 指针慢 11 倍
  - cache 扩容：512 槽 cap 生成阶段 0 命中，9.3GB 显存才 50% 命中
- **结论**：235B 是"能跑"的证明，不是"好用"的招牌。正式 benchmark 主表只放消费级显卡可用的速度数据

---

## 5. 一句话总结

> 从"省内存"（方案 F/路径 1，能跑但慢）到"专家 GPU 化"（A2，方向对但搬运开销大），最终 host-buffer 用**"专家 CPU 驻留 + 调度器按激活专家拷贝 + 热专家缓存"**同时解决了显存和速度两个问题——这是经过十余条路线实测后收敛出的答案，不是拍脑袋的选择。
